# 超温分析：手工台账与共享历史

## 使用顺序

1. 在“超温分析 → 测点台账”建立测点，选择所属机组、名称、测量类型及安装位置；DCS Tag 不详可以留空，系统使用内部编号。相同机组中的 Tag 必须唯一。
2. 对测点新增配置，填写真实生效时间。温度限值及其依据单独维护，材料库里的设计温度不会自动用作报警限值。
3. 选择一个或多个受热面编码区域，预览编码范围，填写图纸/现场确认等依据后确认映射。支持机组、系统、部件、墙位/空间、排屏、小屏、管或回路及 Q/W 部位；不适用字段与“全部”均显式表示。
4. 定期录入温度观察或人工核定的超温区间。先核对记录开始时刻适用的配置版本；跨版本区间需拆分。
5. 在累计分析中按机组、受热面、测点和时间筛选；在管段档案中查看历史配置真正覆盖该编码的温度证据。

## 批量导入

适用于基础测点台账建账和每月 DCS 超温报表入库，入口在“超温分析”页：

- **测点台账 → 导入测点台账**：支持 CSV / XLSX。按“机组 + DCS Tag”匹配，已有 Tag 跳过，不覆盖既有测点；温度限值与依据写入该测点的新配置，配置基线生效时间为 `2000-01-01`，正式依据确认后可再追加版本。导入不会自动确认测点与受热面区域的映射，台账仍显示“待映射”。
- **累计分析 / 温度记录 → 导入月度报表**：支持 DCS 月报 `.xls` / `.xlsx` 与 CSV。按“点位”列匹配已登记测点的 `DCS Tag`，不按描述猜测。

月报列要求：点位、描述、限值、最值、开始时间、结束时间、总时长(秒)。其中“总时长(秒)”在 DCS 导出中实际为 `HH:mm:ss`，导入时解析为秒并与起止时间差核对，偏差超过 5 秒的行会标记为需处理。

导入规则：

- 先预览，再勾选“已核对文件来源、点位匹配和限值”后写入；未确认不会写库。
- 区间温度必须**达到或超过**当时有效配置的限值；等于限值同样计入，低于限值的行会明确标为“低于限值”，不写入、不累计。
- 同一测点同月可有多条事件，全部保留；累计按事件区间并集计算，重叠时段不重复计时。
- 重复上传时按“测点 + 开始时间 + 结束时间”生成稳定记录身份，相同区间跳过；不会重复累计。
- 报表限值与系统配置不一致、区间跨越配置生效边界、测点未登记、缺少有依据限值时，均列入“需处理”，不静默写入。
- 某个月未上传报表表示“未导入”，不能据此认定该月没有超温。

导入只处理报表中已有的越限事件，不会把月报峰值推算成连续温度曲线，也不会自动建立测点与管排区域的映射。

批量创建只用于建立名称序号和内部身份，不自动建立测点与管排的一一对应，也不把截图上的瞬时数值写入业务记录。汽包等未纳入现有管码体系的测点可以建账，暂保持未映射。

## 计时口径

| 记录类型 | 所需依据 | 累计行为 |
| --- | --- | --- |
| 温度观察 | 观测时间、温度、备注 | 只证明该时刻读数；达到或超过限值也不生成持续时间 |
| 已结束超温区间 | 开始、结束、最高温度、整个时段的超温核定及依据 | 温度达到或超过有依据的限值且已核定时计入 |
| 未结束超温区间 | 开始、温度、备注 | 单独显示未结束事件，不把截至现在的间隔计入已确认累计 |
| 作废记录 | 作废原因、操作者和原记录 | 保留历史，不参加统计 |

- 所有区间采用半开范围 `[开始, 结束)`。重叠、包含、重复区间只算一次，相邻区间归并为连续时段。
- 多个测点覆盖同一区域时，区域累计取“任一测点已核定超温”的时间并集；不是测点小时数的求和。单点统计仍保留明细。
- 统计窗口裁剪时长。若一条区间仅部分落入窗口，其整段峰值不一定出现在窗口内，因此不作为精确窗口峰值；单列参考整段峰值。
- 已录入最高温度可能含瞬时观察，不等于整段时间内的平均温度。不能用最高温度乘累计时长当作损伤量。
- 本版本不计算覆盖率、超温占运行小时比例或蠕变寿命。人工记录未覆盖的时间不能解释为未超温。
- 输入、展示统一采用北京时间 UTC+08:00，存储为毫秒时间戳；不受电脑本地时区影响。

## 累计分析可视化

- **月度超温时长**：按自然月拆分跨月区间，统计跨测点区间并集；点击月份可把筛选时间收窄到该月。
- **时段分布**：以北京时间“星期 × 小时”统计累计时长，颜色越深表示该时段超温暴露越长；用于识别交接班、启停或负荷调整时段。
- **测点超温排行**：按各测点自身并集时长排序，显示记录数与峰值；点击条形可筛选到该测点，再结合表格查看明细。
- 图表全部基于当前筛选窗口内已结束、已核定的区间；观测记录、未结束区间和作废记录不参与时长。空图表示当前窗口没有证据，不等于该时段未超温。

## 编码与历史配置

区域范围与当前管码矩阵保持一致，使用规范方向。低过/低再管码未写检修空间时按第1空间解释；区域的“全部空间”是独立的通配设置。悬挂屏入口 F 与出口 B 不能混同，底弯 W 使用对应回路的规范身份。高再按7回路分别关联F入口腿和B出口腿，B不再作为反向管号镜像；超出7回路的历史管位不自动纳入确认范围。

限值、映射和确认依据以配置版本追加保存。每条记录引用其开始时刻适用的版本；改名和停用不会使旧记录消失。新配置不能切入已有有效记录或改变既有记录适用版本；需要先按实际资料更正、拆分或作废相应记录，再新增配置。每次更正均保留原因和审计前后值。

## 管段分析边界

温度模块提供运行工况辅助证据，不改变既有测厚预测的减薄速率、触阈年份、剩余小时数、风险分数或更换预警。集箱壁温、汽温、烟温是区域代表信息，不等于炉管每个位置的实测金属温度。

- 已知最近换管日期：显示从该日北京时间零点起的当前管关联证据，同时保留区域全部历史。既有换管记录只有日期，不能推断更精确的投运时刻。
- 没有明确换管日期：只展示区域历史，不宣称这些时长全部属于当前这根管。
- 未关联、映射待确认、未配限值、无有效记录、读取失败分别展示。任何一种都不能自动标为“正常”。
- 现有远程专家分析入口仅接收必要的温度摘要，继续进行数值审计；不得凭温度摘要生成寿命折减系数。保存测点/记录不会主动调用外部模型。

## 多设备共享及部署

温度记录保存在独立 D1 表，不在 `boiler_user_db` 中。服务端登录身份作为记录人，更新时间由服务器生成。更新携带行版本号，过期版本返回冲突并保留当前表单。创建和更新使用请求 ID 处理网络重试，重复请求不会重复累计。

离线草稿只存在当前浏览器，不代表已经共享，也不计入分析。成功保存后才刷新共享统计；另一电脑进入模块、返回页面或点击刷新即可读取新记录。更正、停用和作废保留审计历史。

数据库初始化顺序：

```bash
npx wrangler d1 execute DB --local --file=migrations/0001_init.sql
npx wrangler d1 execute DB --local --file=migrations/0002_temperature.sql
```

正式部署由既有 GitHub Actions 顺序执行两份 SQL；这两份迁移仅增加不存在的表与索引，重复执行不清除业务数据。代码交付不等于生产数据库已迁移或已经发布。仅静态服务器没有共享 API，页面会明确提示，不会退回假装共享成功的本地台账。

## 验证

本地接口测试使用 Node.js 24 的 `node:sqlite`，CI 已固定 Node.js 24。可运行 `node tests/serve-temperature-preview.mjs` 启动仅监听回环地址的隔离 UI 验收服务；它建立全新的临时 SQLite 库，所有账号/记录均须是合成数据，不是生产 D1。关闭进程后不再提供服务。

首版面向低频人工登记；当前每张温度表超过 20,000 条时接口明确拒绝生成摘要，不静默截断。需要长期高密度运行时序时，应扩展为服务端分区/时段聚合查询，而不是直接导入海量 DCS 数据。

- `tests/overtemperature-core.test.mjs`：区间、限值/映射版本、编码和换管边界。
- `tests/overtemperature-api.test.mjs`：隔离数据库中的行级保存、幂等、并发、分页、审计和迁移。
- `tests/overtemperature-evidence.test.mjs`：辅助证据接线、异步状态和原预测值不变。
- `tests/overtemperature-ui.test.mjs`：页面契约及交互。
- `tests/deployment-data-preservation.test.mjs`：离线执行部署脚本，确认原检修数据、账号和会话保留。

验收数据必须清楚标注为合成数据，放在隔离测试库，不得写入真实现场记录。
